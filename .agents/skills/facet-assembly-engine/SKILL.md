# Facet Assembly Engine

The assembly engine turns the user's full library of components into a vector-specific, page-budgeted, render-ready resume. Touching it without a mental model produces subtle wrongness — the output looks plausible but quietly drops a bullet, misorders a section, or breaks the override system.

This skill is the pocket reference. Authoritative source is the code at `src/engine/`; this is the **shape and the gotchas**.

## The pipeline at a glance

```
ResumeData + AssemblyOptions
   ↓ assembleResume()  (src/engine/assembler.ts:194)
   ↓   resolve priority by vector
   ↓   apply manual overrides (4-level key precedence)
   ↓   resolve text variants per vector
   ↓   resolve {{variables}}
   ↓   apply manual bullet order per role
AssembledResume
   ↓ applyPageBudget()  (src/engine/pageBudget.ts:151)
   ↓   clone, then trim from end while over budget
AssemblyResult { resume, estimatedPageUsage, trimmedBulletIds, warnings }
   ↓ Typst worker  (src/engine/typst.worker.ts)
PDF bytes
```

Each stage is pure modulo cloning. No store reads inside the engine — `assembleResume` is called by `useAssembledResume` (or equivalents) with state read upstream.

## Priority is binary

`ComponentPriority = 'include' | 'exclude'` (`src/types.ts:7`). There is no four-level scale.

A historical four-level system (`must` / `strong` / `optional` / `exclude`) is recognized only at import time by `src/engine/serializer.ts` (see `LEGACY_INCLUDED_PRIORITIES`) — values get normalized to `include`/`exclude` on the way in. Do not write engine code that branches on `must`/`strong`/`optional`; if you see those tokens outside the serializer's normalization path, that's a bug.

`PriorityByVector` is a `Record<VectorId, ComponentPriority>`. Each component carries one entry per vector it's classified against.

## Vector selection semantics

`VectorSelection = VectorId | 'all'`.

- **Specific vector:** a component is included if `vectors[selectedVector] === 'include'`. Missing entry → excluded.
- **`'all'`:** a component is included if **any** vector entry is `'include'`. This is union semantics, not intersection. Used for the library-wide "show everything" view.

Skill groups have a richer model (see `resolveSkillGroupConfig` in `assembler.ts:154`) — they support per-vector content overrides and per-vector ordering.

## The override key system

Each component has up to four override keys, walked in this precedence (most specific wins):

```
1.  role:{roleId}:{type}:{id}      // bullet within a specific role
2.  role:{roleId}:{id}             // shorthand for the same
3.  {type}:{id}                    // type-scoped
4.  {id}                           // bare id
```

Generated by `buildComponentKeys()` (`src/engine/assembler.ts:50`); resolved by `resolveManualOverride()` (`src/engine/assembler.ts:60`). The shared utility `src/utils/componentKeys.ts` is what stores import to write keys.

**Override values:**
- `true` → force include (beats `exclude` priority)
- `false` → force exclude (beats `include` priority)
- key absent → fall through to the next key, then to the auto-priority

**Implication for new component types:** if you add a new component type, you must call `buildComponentKeys('your_type', id, roleId?)` consistently. Drift here silently breaks user overrides.

## The three type tiers — do not collapse

| Tier | Lives in | Carries | Used by |
|------|----------|---------|---------|
| Raw | `src/types.ts` (`TargetLineComponent`, `RoleBulletComponent`, etc.) | `PriorityByVector`, `TextVariantMap`, full editing metadata | Stores, UI editors, library views |
| Assembled | `src/types.ts` (`AssembledTextComponent`, `AssembledRoleBullet`, `AssembledResume`) | One resolved text + id; no priority/vector residue | Engine output, page budget |
| Template | `src/templates/types.ts` (`TemplateResumeData`, `TemplateRole`, etc.) | Render-ready strings only | Typst rendering, registry adapters |

**Rules:**
- Assembled types must not leak back into raw data (no "save this assembled view as a vector").
- Template types must not carry priority or vector metadata. If a template needs to know about vectors, the *adapter* knows; the template type stays render-ready.
- Don't add a fourth tier for "intermediate" shapes. If a stage needs more than the next tier provides, it usually wants a richer assembled type.

## Page budget: clone-then-mutate exception

`applyPageBudget()` is the **single intentional exception** to Facet's no-mutation rule. It:

1. Calls `cloneAssembledResume()` (`src/engine/pageBudget.ts:55`) to deep-clone the input — header links, role bullets, every nested array.
2. Mutates the clone in place via `removeLastBullet()`, which `splice`s from the end of the last role until the page estimate fits.
3. Returns the clone plus `trimmedBulletIds` and any `over_budget_after_trim` warning.

**Don't "fix" this by switching to immutable updates** — the trim loop runs many iterations and the clone-then-mutate pattern is faster and reads more clearly than nested `.map(...)`. But:

- Any new field on `AssembledResume` must be added to `cloneAssembledResume`. Forgetting this aliases user state across calls.
- Trim removes from the **end of the last role** first. If you change ordering rules, the trim semantics change too — usually the wrong call.

## Page estimation is a heuristic

`estimateResumeLines()` (`src/engine/pageBudget.ts:91`) counts wrapped lines from character counts:
- `DEFAULT_LINES_PER_PAGE = 58`
- `DEFAULT_CHARS_PER_LINE = 92`
- `CONTACT_CHARS_PER_LINE = 72`

These are calibrated to the Typst templates' default theme. **Theme changes that affect line height, font size, or margins invalidate the calibration.** When you ship a theme change, sanity-check the estimate against the actual PDF page count for several real fixtures (`src/test/fixtures/`).

The PDF's true page count is computed by Typst (`toPdfPageCount` in `src/utils/typstRendererUtils.ts`); the estimate is the engine's pre-render approximation used for trimming decisions.

## Variant + variable resolution

Two text-substitution layers, applied in order inside `resolveTextVariant()` (`src/engine/assembler.ts:36`):

1. **Vector variant.** If `selectedVector !== 'all'` and `variants[selectedVector]` exists, use it; else fall back to base `text`.
2. **Variable substitution.** `resolveVariables()` from `src/utils/variableResolver.ts` substitutes `{{var}}` tokens against `data.variables` (or `options.variables`).

**Implication:** variant text can itself contain `{{vars}}`. Variables resolve last; design variant text accordingly.

## Rendering: Typst, not DOCX

`docs/development/domain-model.md` mentions a `docx`-based "Editorial Dense" template — that path is **stale**. Real rendering:

- Templates are `.typ` files (Typst source) loaded as raw strings via Vite's `?raw` import (`src/templates/registry.ts`).
- Currently shipped: `classic` (`resume.typ`), `sidebar`, `minimalist`, `letter`.
- Rendering happens in a Web Worker (`src/engine/typst.worker.ts`) so the main thread stays responsive during preview.
- The worker receives `{ templateContent, dataPayload, themePayload, fontFiles }` and returns `{ bytes, pageCount }`. The bytes are transferred (not copied) via `postMessage`'s transfer list.

**Adding a template:** add the `.typ` file, register it in `TEMPLATES`, and ensure the existing `TemplateResumeData` shape is sufficient. If the template needs more fields, extend the *Template* tier types and the adapter — don't reach back into `AssembledResume` from inside the template.

Other renderers exist for non-PDF outputs:
- `src/utils/textRenderer.ts` — plain text export
- `src/utils/markdownRenderer.ts` — clipboard-friendly markdown

## Common pitfalls

- **Mutating `data.roles`** during assembly. Don't — the assembler reads from raw data multiple times. Always build new arrays via `.map`/`.filter`.
- **Forgetting the `'all'` branch.** Vector logic that only handles specific vectors silently breaks the library view.
- **Adding a field to `AssembledResume` without updating `cloneAssembledResume`.** Aliasing bug, hard to debug.
- **Computing override keys ad hoc.** Always use `buildComponentKeys()`; it owns the precedence order.
- **Treating priority as a 4-level scale.** It is binary post-import. Use the serializer normalization, not a runtime branch.
- **Trimming logic that doesn't track `trimmedBulletIds`.** Downstream UI surfaces "what got trimmed" — silent removal degrades the editing feedback loop.
